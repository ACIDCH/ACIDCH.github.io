# Geospatial supply-chain system architecture

## Decision pipeline

```text
Facilities / demand / scenario inputs
  → versioned road graph and typed NetworkMatrix
  → integrated Factory → Warehouse → Demand solve
  → structured mainSolution in geospatialStore
  → fleet, transshipment, inventory and risk consumers
  → Worker Monte Carlo and road-criticality analysis
  → map, Sankey, explainability and chart presentation adapters
```

The map is a renderer. Optimisation modules never recover decisions from marker colours, CSS classes, labels, tooltips or rendered KPI text.

## Model

Factories are upstream supply points only. Warehouses are candidate downstream facilities and may serve demand only when selected. The bounded exact model enumerates admissible warehouse subsets and solves minimum-cost two-echelon flow for each subset. Factory supply, warehouse throughput, demand satisfaction, service threshold, redundancy, must-open / excluded policies and the maximum-open limit are enforced in the same solve. Above the exact candidate limit, deterministic greedy ranking and swap variants are used and the result is labelled `HEURISTIC`.

The fleet model consumes the main solution's Warehouse → Demand assignments. It uses split deliveries, Clarke–Wright savings and 2-opt, validates capacity and depot return, then assigns trips to individual vehicles under per-vehicle shift-hours and trip-count limits.

## Units and network data

`NetworkMatrix` always contains three same-shape matrices:

- `distanceKm` — kilometres;
- `durationMin` — minutes;
- `generalizedCostNZD` — NZD, calculated from explicit per-km and per-minute rates.

Matrix provenance records source, method, version and scenario. Entity edits rebuild the complete affected matrix using one method. A/B monetary deltas are allowed only when metric signatures are comparable.

The built-in Auckland graph is a compact arterial-road OSM snapshot generated by `scripts/build-auckland-baseline.mjs`. Snapshot metadata records source, version, date, node/edge counts and speed assumptions. Live Overpass refresh is optional.

## State and revisions

`geospatialStore.js` owns entities, graph/version, matrices, solutions, service health, scenario slots, route visual records and freshness. Every asynchronous solve begins with a revision token. A result whose revision no longer matches the active scenario is discarded. Input or graph changes invalidate the main result and all downstream results.

## External services

`gisServices.js` centralises Nominatim, OSRM and Overpass. It provides timeouts, bounded retry, response validation, caching, in-flight request deduplication and Nominatim pacing. Overpass tries the primary endpoint before the secondary. Failure states are published to the store; the baseline graph remains usable and fabricated routes are never created.

## Network algorithms

- KD-tree index for point-to-road snapping;
- target-aware and bounded Dijkstra for matrices and coverage;
- cache keyed by graph version, scenario, source and metric;
- admissible A* for single-pair route reconstruction;
- exact bounded warehouse enumeration plus minimum-cost flow;
- deterministic heuristic switching for larger candidate sets.

## Background analysis and risk outputs

Seeded Monte Carlo runs in `geospatial-analysis.worker.js` and reports expected cost, P95, CVaR95, failure rate, expected unmet demand, stockout probability, facility stability and a cost histogram. Worker requests carry the scenario revision; stale results are discarded. If Worker creation fails, the portfolio-scale calculation can run on the main thread and is explicitly labelled `FALLBACK`.

The disruption generator supports congestion, closure, improvement and mixed road perturbations plus correlated Harbour, CBD, warehouse-outage, factory-loss, demand-surge, access-improvement and severe-weather events; it is scenario-based rather than live traffic.

Road criticality selects deterministic candidates from the current optimal-route edges. Each candidate is removed, affected shipments are rerouted, and the system measures the increase in generalised NZD cost, average travel time and unmet demand. The displayed 0–100 score is the normalised sum of non-negative cost increase, weighted delay cost and an explicit NZD 1,000 per-unit unmet-demand penalty. This is route-contingency analysis under the current allocation, not full network interdiction optimisation.

The Sankey is generated from structured Factory → Warehouse and Warehouse → Demand flow objects. Link width is proportional to solved flow. The explainability drawer also reads structured state and exposes assignments, alternatives, utilisation, upstream supply, Fleet trips, risk stability and criticality sensitivity without reading tooltip text or map colours.

## Differential validation

`scripts/benchmark-geospatial.py` runs outside the browser and compares project Dijkstra/A*, minimum-cost flow and exact facility results with NetworkX 3.5. A tiny Fleet case is independently checked against exhaustive TSP permutations. NetworkX is a development-only dependency listed in `requirements-geospatial-benchmark.txt`.

## Data disclosure and limitations

- Road topology: OpenStreetMap / Overpass; optional road tables and geometry: public OSRM; geocoding: Nominatim; basemap: CARTO / OSM.
- Supply, demand, capacity and cost inputs are illustrative portfolio values.
- Public services are best-effort and may throttle or fail.
- The browser heuristic is deterministic but is not a proof of global optimality.
- The fleet model supports split delivery but not delivery time windows or driver breaks.
- Worker fallback can still occupy the main thread on browsers that block module Workers.
- Road criticality tests current high-flow route edges and fixed allocations; it does not exhaustively solve every-edge interdiction or prove enterprise-scale resilience.
- The explainability drawer reports the best alternative under the current matrix rather than solving a separate counterfactual facility model.
