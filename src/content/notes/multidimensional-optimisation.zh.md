## 增加维度，是因为业务需要分得更细

最简单的生产变量可以只有一个：

```text
x = total production
```

如果业务开始区分产品，就变成：

```text
x[p]
```

再区分工厂：

```text
x[k, p]
```

再加入时期：

```text
x[k, p, t]
```

变量越来越长，不是为了让数学显得复杂，而是因为决策本身在不同对象之间已经不一样。

North Plant 和 South Plant 有不同容量，Core 和 Premium 有不同资源消耗，不同时期有不同需求。模型要把这些差异真正保留下来，就必须增加相应维度。

## 0D 到 n-D 可以按“一行变量代表什么”来理解

### 0D：一个总量

\[
x
\]

表示全系统一个总决策，例如总采购量。

### 1D：按一个维度区分

\[
x_p
\]

表示每个产品一个决策。

### 2D：按两个维度区分

\[
x_{k,p}
\]

表示每个工厂、每个产品一个决策。

### 3D：再加入时期

\[
x_{k,p,t}
\]

表示每个工厂在每个时期生产每个产品多少。

更高维度也是同一个逻辑。关键不是记 4D、5D 的名字，而是能把每个 index 翻回业务语言。

如果一个变量 `x[k,p,t]` 无法清楚说出“一条记录代表什么”，模型很容易在后面出现聚合错误。

## 每增加一个维度，变量数都是乘法增长

假设：

```text
2 plants
2 products
4 periods
```

变量 `x[k,p,t]` 的理论数量是：

\[
2\times2\times4=16
\]

如果再加入 3 类原料：

\[
x_{k,p,m,t}
\]

理论组合数变成：

\[
2\times2\times3\times4=48
\]

如果真实业务有 10 个工厂、50 个产品、20 个客户区域、52 周，完全展开的变量数会非常快地增长。

因此，高维建模不能只关心公式有没有写对，还要控制规模有没有必要。

## 维度应该来自业务差异，而不是“能加就加”

是否需要某个 index，可以问一个简单问题：

> 这个维度上的不同对象，是否真的有不同参数、约束或决策意义？

如果所有工厂的生产成本、容量和可生产产品都完全一样，而且管理上也不需要分工厂结果，那么增加工厂维度可能没有价值。

如果不同时期需求差异明显，还要处理库存结转，那么时间维度就很必要。

模型维度越多，数据要求越高。没有可靠参数支撑的细粒度模型，往往只是把不确定性藏在更多单元格里。

## 参数索引必须和变量索引对得上

假设生产变量是：

\[
x_{k,p,t}
\]

单位生产成本可能写成：

\[
c_{k,p,t}
\]

工厂容量可能只需要：

\[
cap_{k,t}
\]

产品需求可能是：

\[
demand_{p,t}
\]

不是所有参数都必须拥有和变量相同的维度。

容量不区分产品，就不应该硬加一个 p；需求只按产品和时期变化，就没有必要再复制工厂维度。

参数维度越精确，越容易看出每个数据究竟作用在哪里。

## 求和符号是在“消掉不需要的维度”

假设要限制 North Plant 在时期 t 的总生产，不论产品：

\[
\sum_p x_{north,p,t}\le cap_{north,t}
\]

这里对 p 求和以后，产品维度被聚合掉，剩下工厂和时期。

如果要计算某产品 p 在时期 t 的总产量：

\[
\sum_k x_{k,p,t}
\]

这次消掉的是工厂维度。

高维模型最值得练习的就是这种阅读：当前约束保留哪些维度，又把哪些维度求和掉。

一旦求错 index，模型可能仍然可解，却在错误层级上控制资源。

## 约束族的维度决定会生成多少条约束

例如每个工厂、每个时期都有一条容量约束：

\[
\sum_p x_{k,p,t}\le cap_{k,t}\qquad\forall k,t
\]

如果有 2 个工厂、4 个时期，就生成：

\[
2\times4=8
\]

条容量约束。

需求约束如果按产品和时期生成：

\[
\sum_k x_{k,p,t}\ge demand_{p,t}\qquad\forall p,t
\]

2 个产品、4 个时期就生成 8 条。

因此，模型规模不仅取决于变量维度，也取决于每组约束保留了哪些 indices。

## State 和 Flow 是高维模型里两种不同变量

供应链模型中常见两类变量。

**Flow** 表示某段时间内发生的数量，例如：

```text
production[k,p,t]
shipment[k,r,t]
```

**State** 表示某个时点保存下来的状态，例如：

```text
inventory[p,t]
backlog[p,t]
```

这两类变量不能随意混在一起。

生产是一个时期内发生的流量，期末库存则是经过生产、需求和上期库存共同作用后的状态。

多期模型里最重要的约束往往正是在连接 state 和 flow：

\[
I_t=I_{t-1}+Production_t-Demand_t
\]

理解这一区别以后，多维生产库存模型会清楚很多。

## 不是每个理论组合都应该创建变量

假设 Premium 只能在 North Plant 生产，那么组合：

```text
(south, premium)
```

根本不合法。

一种做法是仍然创建变量，再强制：

\[
x_{south,premium,t}=0
\]

另一种更紧凑的做法是从一开始就不创建这些变量。

对于大型模型，后者通常更清晰：

```python
valid_plant_product = [
    ("north", "core"),
    ("north", "premium"),
    ("south", "core"),
]
```

这种 sparse combination 能减少变量数，也避免求解器在明显无意义的组合上浪费时间。

## 高维参数最怕“维度错位但数值类型没错”

很多 bug 不会产生 Python error。

例如成本字典是：

```text
(plant, product, period)
```

代码却错误地按：

```text
(product, plant, period)
```

读取。如果两个位置恰好都是字符串，程序可能继续运行，最后只是把错误成本放进了目标函数。

这比明显的 `KeyError` 更危险。

因此，多维参数应该使用明确名称、固定 key 顺序，并在建模前做抽样核对：

```text
North × Premium × P1 的成本是多少？
代码拿到的值是否和源数据一致？
```

少量人工 spot check 非常有用。

## 切片调试比打印整个模型更有效

高维模型出现异常时，直接打印几千个变量基本看不出问题。

更好的办法是固定一部分 indices，只看一个切片。

例如：

```text
只看 P1
只看 North Plant
只看 Premium
```

Python 中可以按条件筛：

```python
for k in plants:
    for p in products:
        value = pl.value(x[k][p]["P1"])
        if value and abs(value) > 1e-8:
            print(k, p, value)
```

如果 P1 的平衡都不对，就没有必要先检查后面 51 周。

从低维切片开始验证，再扩展到整体，是调试高维模型最省时间的方法之一。

## 聚合回算能检查不同维度有没有对齐

求解后，可以把高维结果重新聚合到熟悉的业务数字上。

例如：

```text
按工厂汇总总产量
按产品汇总总产量
按时期汇总总发货量
按区域汇总收到的总量
```

这些汇总应该和容量、需求或已知总量对得上。

如果总生产量是 900，但按产品加总只有 860，说明某个维度在结果整理里漏了。

高维模型的验证不只检查单个变量，也要做 cross-dimension reconciliation。

## Mass balance 是供应链高维模型最重要的检查之一

任何网络流或库存模型都应该能回答：货从哪里来，最后到哪里去。

一个简单平衡可以写成：

\[
Beginning+Inbound+Production=Outbound+Demand+Ending
\]

如果每个节点、每个产品、每个时期都满足平衡，模型至少在数量守恒上是连贯的。

如果只看总量，局部错误可能互相抵消。因此高维模型最好先在最细的有效粒度上检查平衡，再向上汇总。

例如：

```text
product × plant × period
```

平衡通过以后，再汇总成公司总量。

## 结果展示应该“降维”回业务语言

模型内部用 4D、5D 变量没有问题，但管理者通常不需要看到整个张量。

结果页面更适合回答：

```text
哪个工厂承担最多产量？
哪个产品造成容量瓶颈？
哪几个时期库存最高？
哪些路线实际被使用？
```

可以把高维结果做成：

- 按时期折线；
- 工厂 × 产品表；
- 路线流量矩阵；
- 只显示非零组合；
- 关键时期的明细切片。

复杂度应该留在模型内部，解释层要重新整理成可以决策的信息。

## 一套更稳妥的高维建模顺序

1. 先写清楚一条变量代表什么；
2. 只加入业务上确实需要区分的维度；
3. 给每个 set 和 index 固定含义；
4. 检查参数 key 的顺序和完整性；
5. 预估变量数和约束数；
6. 排除无意义组合，优先使用 sparse indexing；
7. 用求和符号明确每条约束聚合掉哪些维度；
8. 分清 state variable 和 flow variable；
9. 用切片检查局部结果；
10. 用 mass balance 和多方向聚合做 reconciliation；
11. 最后把高维结果降维成业务可读的图表和汇总。

多维优化并不是把更多下标写进变量。真正的难点是：每一个下标都有清楚的业务含义，而且变量、参数、约束和结果在这些维度上始终保持一致。
