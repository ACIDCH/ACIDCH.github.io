## 现实决策几乎总有边界

无约束模型可以先看目标函数本身，但真正进入生产、运输或库存问题以后，资源限制马上就会出现。

材料有上限，人工有上限，仓库有容量，车辆有载重，需求可能必须满足，某些订单还有最低服务要求。优化的任务于是从“哪里最好”变成：

> **在所有允许执行的方案里，哪一个最好？**

约束不是模型旁边的备注，它直接定义了哪些方案有资格进入比较。

## 用两种产品把问题写出来

继续使用 Core Kit 和 Premium Kit。

设：

\[
x_C=\text{Core Kit 产量}
\]

\[
x_P=\text{Premium Kit 产量}
\]

单位贡献分别为 42 和 58，所以目标是：

\[
\max Z=42x_C+58x_P
\]

每件 Core 消耗 3 单位材料、2 单位人工；每件 Premium 消耗 4 单位材料、5 单位人工。

材料只有 240：

\[
3x_C+4x_P\le240
\]

人工只有 250：

\[
2x_C+5x_P\le250
\]

再加：

\[
x_C,x_P\ge0
\]

这几条式子一起决定了可以生产哪些组合。

## 可行域就是所有“做得到”的方案

把两条资源约束画在坐标平面上，会出现两条边界线。

材料边界：

\[
3x_C+4x_P=240
\]

人工边界：

\[
2x_C+5x_P=250
\]

每条不等式都对应边界线的一侧。再加非负条件，最后留下的交集就是 feasible region。

例如：

```text
x_C = 20
x_P = 20
```

材料使用：

\[
3(20)+4(20)=140\le240
\]

人工使用：

\[
2(20)+5(20)=140\le250
\]

所以这个方案可行。

如果换成：

```text
x_C = 60
x_P = 40
```

材料需要 340，已经超过 240，因此它根本不在可行域里。目标值再高也没有比较意义。

## Equality 和 inequality 表达的是不同业务规则

约束常见两种形式。

等式：

\[
x_1+x_2=100
\]

表示必须刚好满足某个平衡关系，例如需求完全由两个来源覆盖。

不等式：

\[
x_1+x_2\le100
\]

表示最多只能用 100。

另一种：

\[
x_1+x_2\ge100
\]

表示至少要达到 100。

符号选错会直接改变可行域。比如“最多使用 250 工时”写成 `>=250`，求解器仍然能正常计算，但业务含义已经完全反了。

所以写约束时最好先用一句中文说清楚“最多”“至少”还是“必须等于”，再翻成符号。

## 非负约束不能想当然地省略

产量、运输量和库存通常不能为负，所以：

\[
x_C,x_P\ge0
\]

很自然。

但数学模型不会自动理解“产量不可能是 -10”。如果建模工具默认变量可以取负，而代码里又没有设置下界，模型可能利用负数得到一个毫无业务意义的答案。

同样地，某些变量还需要：

```text
integer
binary
upper bound
```

变量边界是模型定义的一部分，不是求解完成以后再补的解释。

## 为什么线性规划常在角点找到最优解

在线性规划中，目标函数是一组平行线：

\[
42x_C+58x_P=Z
\]

把这条线向贡献更高的方向平移，最后还能碰到可行域的位置通常是某个角点或一段边界。

当前模型的主要角点包括：

```text
(0, 0)
(80, 0)
(0, 50)
两条资源边界的交点
```

两条边界联立：

\[
3x_C+4x_P=240
\]

\[
2x_C+5x_P=250
\]

解得：

\[
x_C=\frac{200}{7}\approx28.57
\]

\[
x_P=\frac{270}{7}\approx38.57
\]

目标值：

\[
Z\approx3437.14
\]

比较各角点后，这个交点最好。

## Binding constraint 表示资源刚好被用完

把最优解代回材料约束：

\[
3\left(\frac{200}{7}\right)+4\left(\frac{270}{7}\right)=240
\]

人工约束：

\[
2\left(\frac{200}{7}\right)+5\left(\frac{270}{7}\right)=250
\]

两条都刚好等于上限，因此在最优解上它们都是 binding constraints。

直观地说，这两类资源都真正限制了当前目标。想继续提高贡献，至少要改变其中一条资源边界或产品经济参数。

Binding 并不代表“这条约束最重要”，只是说明在当前最优点上没有剩余空间。

## Slack 告诉资源还剩多少

对 `<=` 约束，slack 可以理解为：

\[
Slack=Capacity-Usage
\]

如果某个方案只用了 220 单位材料，而容量是 240，那么材料 slack 是 20。

在当前最优解中：

```text
Material slack = 0
Labour slack   = 0
```

但如果换一个问题，某条资源可能还有很多 slack。此时增加那项资源通常不会马上改善目标，因为模型本来就没把它用满。

这也是后面做敏感性分析时很重要的起点：先看哪些约束 binding，哪些资源还有余量。

## 数值上“接近 0”也可能算 binding

实际求解器使用浮点计算，结果可能出现：

```text
239.99999998
```

而不是精确的 240。

所以程序里判断 binding 时，不应该直接写：

```python
usage == capacity
```

更稳妥的是设置一个容差，例如：

```python
abs(capacity - usage) < 1e-6
```

这是一个很小的技术细节，却能避免把数值误差误判成真实 slack。

## 冗余约束不会改变答案，却会增加理解成本

有些约束虽然写在模型里，但实际上永远不会比其他约束更紧。

例如：

\[
x_C+x_P\le1000
\]

在材料和人工限制已经把产量压得远低于 1000 的情况下，这条约束几乎不起作用。

这种约束叫 redundant constraint。

它不一定让结果错误，但会增加模型维护和解释负担。大型模型里如果有很多重复或被支配约束，求解效率也可能受影响。

建模完成以后，检查哪些约束始终有巨大 slack，有助于发现是否存在不必要的规则。

## 不可行模型要按约束冲突来查

如果模型返回 `Infeasible`，不要把它理解成“求解器失败”。更多时候，是业务规则之间没有共同交集。

常见原因包括：

- 最低需求总量超过总产能；
- 多个下限叠加以后超出资源；
- 上下界写反；
- 单位或时间周期不一致；
- 二进制逻辑把所有路线都关掉。

排查时可以先暂时放松一组约束，看看可行性是否恢复，再逐步缩小冲突范围。

真正需要修复的是模型输入或业务规则，而不是强行让求解器给出一个“最接近的答案”。

## 资源边界一动，最优点也可能跟着动

假设材料从 240 增加到 250，原来的可行域会向外扩张。最优点可能移动，目标值也可能提高。

但如果人工仍然很紧，材料增加 10 单位不一定全部有价值。新增资源的真正价值取决于其他约束共同形成的边界。

这正是 constrained optimisation 和 sensitivity analysis 的连接处：

```text
当前解在哪个角点？
哪些约束 binding？
如果 RHS 改变，角点怎样移动？
目标值能改善多少？
```

只看“资源已经用满”还不够，下一步要看放宽它到底值多少钱。

## 一套更稳妥的检查顺序

1. 先确认每个变量的单位、下界和类型；
2. 用业务语言逐条解释约束；
3. 画出或抽样检查几个可行和不可行方案；
4. 求解后把最优变量代回所有约束；
5. 计算 slack，识别 binding constraints；
6. 用容差处理浮点误差；
7. 检查是否存在明显冗余约束；
8. 如果不可行，按约束冲突排查；
9. 最后再讨论改变资源边界会带来什么影响。

受约束优化的核心并不只是“有几条不等式”。真正有用的是看清哪些业务边界正在限制决策，以及模型为什么把最优解推到了那个位置。
