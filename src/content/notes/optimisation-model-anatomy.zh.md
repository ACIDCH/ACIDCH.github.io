## 优化不是“让软件找一个最大值”

优化模型的真正工作并不从 Solver、Python 或某个算法开始，而是从一个更基础的问题开始：

> **究竟要决定什么，什么已经知道，什么必须遵守，以及什么结果才算更好？**

如果这四件事没有说清楚，即使求解器返回 `Optimal`，模型也可能回答了错误的问题。

供应链问题常常同时包含成本、服务、产能、时间、网络结构和商业规则。例如“降低配送成本”听起来像目标，但仍然缺少大量信息：配送量是否可以改变？客户需求必须完全满足吗？仓库是否可以关闭？是否允许缺货？运输商是否有最低承诺量？不同决策发生在同一周还是跨多个时期？

因此，优化模型首先是一种**业务语言的结构化翻译**。

## 四个核心部分构成模型骨架

### Objective：什么结果需要被优化？

Objective function 把业务偏好压缩成一个可比较的数值。

常见目标包括：

- 最小化运输、生产、库存、缺货或固定设施成本；
- 最大化利润、贡献、服务覆盖或资源利用价值；
- 在多个目标之间建立加权或分层取舍。

例如产品组合模型可以写成：

```text
max Z = 42·Core + 58·Premium
```

这里的 `42` 与 `58` 是单位贡献，`Core` 与 `Premium` 是要决定的生产数量。

目标函数不是业务问题的全部。它只回答“如何比较两个可行方案哪个更好”。如果方案本身不满足业务规则，目标值再漂亮也没有意义。

## Parameters：哪些值在当前模型中被视为已知？

Parameters 是模型输入，而不是求解器要选择的值。

例如：

```text
单位运输成本
客户需求
工厂产能
单位材料消耗
固定开仓成本
每期库存持有成本
```

一个值在现实中可能会变化，但在某一次确定性模型运行中仍然可以被当作参数。例如下周需求预测可能并不“永远固定”，但在当前基准情景中可以先作为已知输入。

参数设计要特别注意三件事：

1. **单位一致**：kg、箱、工时、成本单位不能混用；
2. **粒度一致**：周需求不能直接和日容量比较而不做转换；
3. **来源明确**：参数来自实际记录、预测、合同还是管理假设，会影响结果可信度。

## Decision Variables：模型真正能够改变什么？

Decision variable 是优化模型的核心。

如果问题是产品组合：

```text
x_core    = Core Kit 生产量
x_premium = Premium Kit 生产量
```

如果问题是配送网络：

```text
x[k,r] = 从工厂 k 运往区域 r 的数量
```

如果问题还要决定仓库是否开启：

```text
y[h] ∈ {0,1}
```

决策变量的类型本身就包含业务语义：

```text
Continuous variable
→ 数量可以连续变化，例如吨数、流量、工时

Integer variable
→ 只能取整数，例如车辆数、员工数、批次数

Binary variable
→ 只能取 0/1，例如开/不开、选/不选、启用/不启用
```

变量类型选错会改变问题本身。把“是否开仓”建成 0 到 1 之间的连续变量，就可能得到 `0.43 个仓库` 这种没有业务意义的解。

## Constraints：什么规则不能被最优目标突破？

Constraints 定义可行域。

例如两种产品共享材料与人工：

```text
3·Core + 4·Premium ≤ 240    material
2·Core + 5·Premium ≤ 250    labour
Core ≥ 0
Premium ≥ 0
```

这些约束不是“建议”。它们决定哪些方案根本不允许进入比较。

供应链模型中的约束通常来自：

- 物理容量：工厂、车辆、仓库、生产线；
- 流量平衡：进入、流出、库存结转；
- 需求满足：全部满足、最低服务水平或允许缺货；
- 合同条款：最低采购量、最大承运量、捆绑选择；
- 逻辑关系：开仓后才能发货、启用功能后才有额外容量；
- 时间关系：本期库存成为下期初始库存。

## 从业务句子到数学表达，不要跳步

一句“满足所有客户需求”至少需要先问：

```text
需求按客户、区域还是产品定义？
每个需求必须恰好满足，还是至少满足？
允许超额配送吗？
允许延期或缺货吗？
需求发生在哪个时期？
```

不同回答会形成不同约束：

```text
Σ supply = demand
Σ supply ≥ demand
Σ supply + shortage = demand
begin_inventory + supply - demand = end_inventory
```

因此，数学符号不是为了让模型看起来复杂，而是为了消除自然语言中的模糊空间。

## 目标、约束与 KPI 不能混成同一层

现实管理问题经常同时出现多个指标，例如：

```text
运输成本
服务水平
库存周转
碳排放
供应商集中度
```

这些指标并不一定都应该进入目标函数。

一个指标可以有三种不同角色：

```text
Objective
→ 希望在可行范围内尽可能优化

Constraint
→ 必须达到的底线或上限

Reporting KPI
→ 不参与求解，但用于解释方案质量
```

例如“准时交付率至少 96%”如果是硬性服务承诺，更适合写成约束，而不是和成本任意加权。相反，如果企业愿意在成本与服务之间进行连续权衡，则可以把服务损失转成有明确业务依据的 penalty。

又例如碳排放可能暂时只是结果 KPI：模型先最小化成本，求解后再报告每个方案的排放。如果排放已经存在法规上限，则应升级成约束。如果企业设置内部碳价，也可以进入目标函数。

这种角色区分能避免一个常见错误：为了“让模型考虑更多因素”，把所有 KPI 直接相加。不同指标具有不同单位和管理优先级，没有清晰尺度与权重时，简单相加只会制造一个难以解释的数字。

## 参数、派生量与决策结果也要分清

模型里经常出现一些看似“输入”的数字，其实是由其他变量计算出来的结果。

例如：

```text
工厂容量利用率
= 实际产量 / 可用容量
```

如果实际产量由模型决定，那么利用率不是独立 parameter，而是求解后的 derived metric。

类似地：

```text
总运输成本
总库存成本
服务覆盖率
资源 slack
```

通常都由变量和参数共同计算。

把派生量误当成独立输入，会出现重复定义甚至逻辑冲突。例如一边让模型决定发货量，一边又把“总运输成本”作为固定输入，就失去了成本随发货方案变化的联系。

因此建模前可以把数据分成三类：

```text
Known inputs
→ 当前情景已经给定的参数

Decision outputs
→ 求解器需要选择的变量

Derived outputs
→ 由参数和变量计算得到的指标
```

这种分类对 Excel 模型尤其重要，因为输入格、changing cells 和公式结果格如果混在一起，很容易造成 Solver 引用错误。

## 可行解与最优解是两个阶段

优化分析最容易被忽略的区别是：

```text
Feasible solution
→ 满足所有约束

Optimal solution
→ 在所有可行解中目标最好
```

一个低成本方案如果违反容量，就不是“次优”，而是**不可行**。

同样，如果模型显示 `Infeasible`，应该先寻找互相冲突的约束和错误参数，而不是继续讨论目标值。

## 模型边界决定结论边界

任何优化模型都是现实的抽象。

例如配送成本模型没有包含碳排放、可靠性或合同风险，那么“最低成本方案”只能解释为：

> 在当前纳入的成本和约束口径下，该方案目标值最低。

它不能自动升级成“企业应该选择这个方案”。

因此模型解释需要同时说明：

- 哪些因素已经进入目标；
- 哪些因素只作为约束；
- 哪些因素完全没有建模；
- 哪些参数存在明显不确定性。

## 最优值是决策基准，不一定是机械执行指令

假设数学模型给出某个资源容量的最优值为 600，但现实采购只提供 575、600、625 三种标准规格。

正确分析不是简单说“600 是最优，所以必须买 600”。

更有价值的问题是：

```text
575 相对理论最优损失多少？
625 相对理论最优损失多少？
标准规格能否减少排班、采购或实施复杂度？
这个便利是否值得对应的目标损失？
```

优化的意义是把取舍量化，让管理者知道偏离最优需要付出多少，而不是把管理判断替换成一个小数点很多的答案。

## 建模前需要锁定粒度

同一个“产量”变量可能有完全不同的维度：

```text
x                       一个总产量
x[p]                    每个产品的产量
x[k,p]                  每个工厂 × 产品的产量
x[k,p,r]                工厂 × 产品 × 客户区域的流量
x[k,p,r,t]              再增加时期
```

变量维度不是代码细节。它决定模型能表达哪些现实差异，也决定参数和约束应该如何索引。

如果成本在不同工厂不同，但变量只记录产品总量，那么模型根本没有位置表达“在哪个工厂生产”。

## 粒度过粗与过细都会产生问题

粒度过粗时，模型会丢掉关键业务差异。

例如把三个客户区域的需求合并成一个总需求：

```text
total demand = 860
```

如果不同区域运输成本不同，仅保留总量后就无法判断货应该送到哪里，也无法检查每个区域是否被满足。

粒度过细则会引入不必要的变量和参数。例如业务只按周制定产量，却把决策细化到每小时，模型规模会急剧增加，同时需要大量并不存在或不可靠的小时级参数。

因此粒度设计需要回答：

```text
这个维度是否改变成本？
是否改变容量？
是否改变需求或服务规则？
是否改变可执行决策？
结果是否真的需要在这个层级落地？
```

只有当答案至少有一项明确为“是”时，增加维度才通常具有建模价值。

## 先建立单位表，再建立公式

很多优化错误不是算法问题，而是量纲错误。

可以为关键参数建立一个简单的单位表：

| 参数 | 业务含义 | 单位 |
|---|---|---|
| `demand[r]` | 区域需求 | units/week |
| `capacity[k]` | 工厂周产能 | units/week |
| `transportCost[k,r]` | 单位运输成本 | cost/unit |
| `labourUse[p]` | 单件人工需求 | hours/unit |
| `availableLabour` | 可用人工 | hours/week |

然后检查约束左右两边：

```text
hours/unit × units = hours
```

因此：

```text
Σ labourUse[p] · x[p] ≤ availableLabour
```

在量纲上成立。

如果左边是 `hours/week`，右边却是 `hours/day`，求解器不会报语法错误，但整个结果都建立在错误尺度上。

## 模型验证至少需要四层检查

求解器返回结果后，可以分四层验证。

### 结构检查

确认：

```text
变量数量是否符合预期？
约束数量是否符合预期？
binary/integer domain 是否正确？
每个业务对象是否都进入了对应集合？
```

### 数值检查

独立重算：

```text
目标值是否等于各项成本或贡献之和？
资源使用是否超过容量？
需求是否完全满足？
库存平衡是否逐期成立？
```

### 边界检查

检查极端情景：

```text
需求为 0 时模型应该发生什么？
容量非常充足时哪个约束应变成 slack？
所有设施关闭时是否正确变成 infeasible？
单位成本交换高低后路线选择是否符合直觉？
```

### 业务检查

最后判断：

```text
方案是否可以执行？
是否遗漏合同或政策规则？
结果是否依赖一个明显不可靠的参数？
最优方案与现有流程相比为什么不同？
```

四层检查的意义在于避免“代码能跑 + Solver 显示 Optimal”被误当成完整验证。

## 一个可审计的建模顺序

建议始终按下面的顺序检查：

```text
1. Business question
2. Sets / indices
3. Parameters
4. Decision variables
5. Objective
6. Constraints
7. Variable domains
8. Solve status
9. Decision values
10. Constraint diagnostics
11. Sensitivity / scenario checks
12. Managerial interpretation
```

这套顺序可以同时用于 Excel Solver、数学公式和 Python/PuLP。

## 建模文档应该能让另一位分析者重建模型

可审计性意味着模型说明不能只写：

```text
使用 Solver 找到最优生产组合。
```

更完整的记录至少应让读者知道：

```text
决策变量及单位
目标函数及方向
每组约束的业务来源
参数表及时间粒度
变量 domain
求解器状态
关键结果
验证步骤
敏感性范围
```

如果这些信息齐全，即使换成另一种工具，也能够重建同一个业务模型。工具只是实现方式，模型逻辑本身才是可复用资产。

这也为后续从 Excel 迁移到 Python/PuLP 提供基础：只要数学结构和数据口径稳定，技术实现可以升级，而不需要重新猜测业务规则。

## 常见错误

### 目标和决策变量混在一起

“最小化仓库数量”是目标，而“是否开仓”是决策变量。两者职责不同。

### 把可变输入误当参数

如果采购量本来可以由模型选择，却被写死成参数，模型就失去了这项决策能力。

### 约束只写在文字解释里

如果业务规则没有进入模型公式，求解器不会自动遵守。

### 目标单位混乱

把成本、服务率和排放直接相加，需要明确尺度和权重；否则数值大小可能只是单位造成的。

### 看到 Optimal 就停止

求解状态只能证明当前数学模型被求解。数据是否合理、业务口径是否正确、结果是否稳健仍需要独立检查。

## 核心判断

优化模型可以压缩成一句话：

> **Parameters 描述当前世界，Decision Variables 描述可以改变的动作，Constraints 描述不能违反的规则，Objective 描述如何比较所有可行动作。**
