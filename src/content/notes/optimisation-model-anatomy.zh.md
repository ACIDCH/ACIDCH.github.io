## 优化建模先回答“到底要决定什么”

优化问题经常被说成“找最大值”或“把成本降到最低”，但真正困难的部分通常发生在求解之前。

假设一家工厂生产 Core Kit 和 Premium Kit。两种产品都有贡献利润，也都会消耗材料和人工。业务希望提高总贡献，但材料只有 240 单位，人工只有 250 单位。

这个问题一旦说完整，模型才开始出现轮廓：

```text
要决定什么？
→ 两种产品各生产多少

什么已经知道？
→ 单位贡献、单位资源消耗、资源上限

什么不能违反？
→ 材料和人工不能超量

什么结果更好？
→ 总贡献更高
```

这四句话比任何求解器设置都重要。模型如果在这里理解错了，后面即使显示 `Optimal`，得到的也只是“错误问题的最优答案”。

## 一个优化模型通常有四块骨架

绝大多数基础优化模型都能拆成四类东西：

```text
Objective
Parameters
Decision Variables
Constraints
```

它们的角色并不一样。

**Objective** 说明什么叫“更好”；**Parameters** 是已经给定的数据；**Decision Variables** 是模型可以选择的量；**Constraints** 划出哪些选择允许存在。

把这四类内容混在一起，是建模时最常见的错误之一。比如“材料用量 3”是参数，不是决策；“材料不能超过 240”是约束，不是目标；“Core 生产多少”才是模型需要决定的变量。

## 目标函数要对应真正的管理目标

Core Kit 的单位贡献是 42，Premium Kit 的单位贡献是 58。设：

\[
x_C=\text{Core Kit 产量}
\]

\[
x_P=\text{Premium Kit 产量}
\]

如果业务目标是最大化总贡献，可以写成：

\[
\max Z=42x_C+58x_P
\]

这个表达式很短，但它默认了很多东西：贡献已经把需要扣除的变动成本处理好了；两种产品的单位贡献在当前决策范围内不变；业务真正关心的是总贡献，而不是收入、销量或服务水平。

所以写目标函数前，最好先问一句：这个数字变大以后，管理上真的一定更好吗？

有些问题表面上说“降低成本”，实际上还要求满足服务水平；有些问题说“提高产量”，但真正希望最大化的是利润。目标写错，比算法选错更麻烦。

## 参数是输入，不是模型自己猜出来的

当前产品数据是：

| 产品        | 单位贡献 | 材料用量 | 人工用量 |
| ----------- | -------: | -------: | -------: |
| Core Kit    |       42 |        3 |        2 |
| Premium Kit |       58 |        4 |        5 |

资源上限：

```text
Material capacity = 240
Labour capacity   = 250
```

这些数字进入模型以后被当作已知参数。

参数可以来自历史数据、合同、工程标准、预测或管理假设。来源不同，可信度也不同。优化模型不会自动判断 240 是准确产能还是一个过时估计，所以参数质量必须在模型外先被检查。

一个很实用的习惯是给参数带上单位：

```text
42   contribution / Core Kit
3    material units / Core Kit
240  material units available
```

只要单位对不上，公式很可能也有问题。

## 决策变量要能直接回答最后的业务动作

这个例子里的变量是：

\[
x_C\ge0,\qquad x_P\ge0
\]

如果最后的推荐是“生产 28.57 个 Core 和 38.57 个 Premium”，就要继续问：产品是否允许连续数量？

如果产品必须按整件生产，变量应当是整数；如果模型处理的是吨、小时、容量份额等可分割量，连续变量就很自然。

变量类型不是技术细节。它决定了模型允许什么样的答案。

常见变量包括：

```text
连续变量
→ 产量、运输量、工时、库存

整数变量
→ 车辆数、班次数、设备数

二进制变量
→ 开不开仓库、选不选供应商、启不启用路线
```

一个好变量的名称最好能直接说出业务含义，而不是只写成 `x1`、`x2` 后再靠旁边的注释猜。

## 约束把现实规则写进模型

Core 每件用 3 单位材料，Premium 每件用 4 单位材料。材料总量不能超过 240：

\[
3x_C+4x_P\le240
\]

人工约束是：

\[
2x_C+5x_P\le250
\]

再加非负条件：

\[
x_C,x_P\ge0
\]

这些约束一起定义了模型的可行空间。

约束最重要的不是形式，而是来源。每一条约束都应该能对应一句清楚的业务规则：

```text
材料不能超库存
人工不能超可用工时
需求必须满足
运输量不能超过承运能力
某设施不开启时不能向它分配流量
```

如果一条公式说不出对应的业务含义，就值得重新检查。

## 单位检查能发现很多低级错误

优化模型里的每条式子都应该在单位上成立。

材料约束左边：

```text
3 material/Core × x_C Core
+
4 material/Premium × x_P Premium
```

结果单位都是 material，右边的 240 也是 material，所以可以比较。

如果把“每件利润”误放进材料约束，或者把月度需求和周度产能直接相加，即使求解器能运行，模型也已经失去意义。

单位检查尤其适合在模型变大以后使用，因为复杂模型最容易出现的并不是高深数学错误，而是索引、时间周期和量纲错位。

## 粒度决定模型到底在做多细的决策

“生产多少”听起来很明确，但还可以继续拆：

```text
全公司总产量
工厂产量
工厂 × 产品产量
工厂 × 产品 × 周产量
```

粒度越细，模型越接近真实业务，也会带来更多变量和参数。

如果决策真正发生在“工厂 × 产品 × 周”，却只建一个公司总量模型，模型可能给出一个看起来最优、实际上无法执行的答案。

反过来，如果管理层只需要做季度容量判断，把模型细化到每个小时也会增加没有必要的复杂度。

粒度应该跟决策发生的层级一致，而不是越细越高级。

## 模型边界要在求解前说清楚

任何优化模型都会省略现实的一部分。问题不在于“有没有省略”，而在于省略的内容是否会改变当前决策。

例如这份产品组合模型没有写需求上限、换线时间、良率差异和最低批量。如果这些因素在当前业务中确实存在，就要判断它们属于三种情况中的哪一种：

```text
已经包含在参数里
→ 例如单位贡献已经扣除了稳定的变动成本

对当前决策影响很小
→ 可以暂时省略，但要写明边界

会直接改变可行方案
→ 应该进入变量、目标或约束
```

这一步能防止模型越来越复杂，也能避免另一种极端：为了保持公式简单，把真正决定答案的规则全部留在模型外。

一个很实用的做法是保留一份“模型不包含什么”的清单。这样结果交给其他人时，不会让“最优”听起来像对所有现实条件都成立。

## 求解前先用几个手工方案做 sanity check

模型还没有交给 Solver 时，就可以手算几个很简单的方案。

只生产 Core：

\[
x_P=0
\]

材料允许的 Core 上限是 80，人工允许的上限是 125，因此真正上限是 80。

只生产 Premium：

\[
x_C=0
\]

材料允许 60，人工只允许 50，因此真正上限是 50。

这两个边界点至少告诉了三件事：变量数量级是否合理、约束方向有没有写反、资源系数是否大致符合预期。

求解器之后如果返回 `Core = 800`，就可以立即判断模型表达有问题，而不是先相信 `Optimal` 状态。大型模型也可以采用同样思路：挑几个极端或简单业务情景，先确认模型反应符合常识，再进行正式求解。

## 先检查可行性，再比较谁更优

优化模型并不是任何时候都有解。

例如，如果要求同时生产至少 60 个 Core 和 60 个 Premium，那么材料需求是：

\[
3(60)+4(60)=420
\]

已经超过 240。此时模型不可行，不存在一个“再聪明一点的算法”能解决这个矛盾。

因此，看到 `Infeasible` 时，第一反应应该是检查约束之间是不是互相冲突：

- 最低需求是否超过总产能；
- 多条下限是否一起挤爆资源；
- 单位是不是混用了；
- 二进制逻辑有没有把所有选择都关掉。

可行性是最优性的前提。一个不可行模型没有“第二优方案”，只有需要重新检查的业务规则或数据。

## 最优点也要经过业务复核

对当前两产品模型，最优连续解位于两个资源约束的交点：

\[
x_C=\frac{200}{7}\approx28.57
\]

\[
x_P=\frac{270}{7}\approx38.57
\]

目标值约为：

\[
Z\approx3437.14
\]

材料使用量：

\[
3x_C+4x_P=240
\]

人工使用量：

\[
2x_C+5x_P=250
\]

两种资源都刚好用满。

数学上这是一个很干净的答案，但真正交付前还要继续检查：产品是否必须取整数？有没有最低生产批量？需求上限是否存在？切换产品是否有 setup cost？资源容量是不是确实能同时达到标称上限？

“最优”只对已经写进模型的规则负责。

## Near-optimal 方案有时比唯一最优点更实用

管理决策不一定非要死守一个精确最优点。

如果另一个方案只让目标值下降 0.5%，却更容易排班、更符合整批生产、或者给关键资源留出缓冲，那么它可能更适合执行。

因此，优化结果最好同时看：

```text
Optimal solution
Near-optimal alternatives
Resource slack
Decision stability
```

一个模型真正有用，不只是因为它给出最高的目标值，而是因为它能说明偏离最优一点到底要付出多少代价。

## 建模时最值得避免的几种习惯

### 先写代码，再补业务含义

代码能运行不等于模型定义正确。先把变量、目标和约束用文字写清楚，通常更省时间。

### 把 KPI 直接当目标函数

“销量高”“客户满意度高”“库存低”可能同时重要，但必须明确哪些是目标，哪些是约束，哪些只是结果指标。

### 不写变量边界

没有非负、上限、整数或二进制条件，求解器会按照数学允许的范围寻找答案。

### 忽略单位和时间尺度

周需求与月产能、件数与吨数混在一起，是比算法问题更常见的错误来源。

## 一套更稳妥的建模顺序

可以按下面的顺序把业务问题翻成优化模型：

1. 用一句话写清楚最终要决定什么；
2. 列出已经知道的参数和单位；
3. 定义决策变量及其类型、索引和边界；
4. 写目标函数，并确认它真的代表“更好”；
5. 把每条业务规则写成约束；
6. 检查单位、粒度和时间尺度；
7. 写清楚模型边界，并手算几个 sanity-check 方案；
8. 先确认模型可行；
9. 求解后重新计算资源使用量和目标值；
10. 再讨论最优解是否可执行，以及附近有没有更稳妥的方案。

优化建模的核心并不是让软件替业务做决定，而是把决策问题写得足够清楚，让每一个数字、每一条规则和最后的答案都能被追溯。
